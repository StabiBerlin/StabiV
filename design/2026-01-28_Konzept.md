# Konzept zum Qualitätsprüfungstool

Dieses Dokument beschreibt das grundlegende Konzept zum Qualitätsprüfungstool, die dafür einzusetzende Open-Source-Software, sowie die Kommandozeilenschnittstelle.

## Überlegungen zur Architektur

### Erfahrungswerte

- Gemäß Spk-Berlin: "Exiftool erkennt mehr als JHOVE"

### Kompatibilität mit Kitodo.Production

- Die zu entwickelnde Software besteht im Idealfall vollständig aus OpenSource Java-Bibliotheken, sodass
  - Kitodo.Production diese direkt einbinden und über eine API ansteuern kann
  - bei der Installation von Kitodo.Production keine zusätzliche Software separat installiert werden muss
  - spezifische Versionen der Softwarebibliotheken fixiert werden können

### Nachnutzung von Kommandozeilenprogrammen

Bei der Nachnutzung von Kommandozeilenprogrammen (wie `exiftool`) im Sinne einer API, ergeben sich im Vergleich zur Einbindung einer Softwarebibliothek unter Umständen zusätzliche Probleme:

Problem: Mögliche Nachverarbeitung der exakten Metadaten
- eventuell werden zur Darstellung in der Kommandozeilenausgabe Metadatenwerte zur besseren Lesbarkeit weiterverarbeitet, z.B. überschüssige Leerzeichen entfernen oder Sonderzeichen weggelassen oder transformiert
- Mögliche Lösung: Nachlesen im Quelltext
- Mögliche Lösung: Ausgabeformate wie XML nutzen

Problem: Metadatenherkunft teils unklar
- fehlt die Angabe der exakten Tiff Tag ID, ist nicht klar, wo die Metadatenwerte exakt abgelesen wurden
- z.B. bei generisch Angaben wie "Bildbreite" und "Bildhöhe" ist unklar, ob die Information aus den Metadaten kommt, oder von den Bilddaten abgeleitet wurde
- Mögliche Lösung: Nachlesen im Quelltext

Problem: Keine Kontrolle über Softwareversionen
- das Kommandozeilenprogramm (z.B. `exiftool`) kann je nach Betriebssystemversion in unterschiedlichen Versionen vorliegen
- Mögliche Lösung: Binaries mitliefern
- Mögliche Lösung: Docker

Problem: Nachnutzung in Kitodo.Production
- Bei einer Nachnutzung in Kitodo.Production muss das Tool als Teil der Installationsanweisungen mit installiert werden, oder als Binary mitgeliefert werden

### Zukünftige Weiterentwicklung als GUI

Prinzipiell ist es möglich mit Java zusätzlich eine graphische Benutzerschnittstelle (GUI) zu entwickeln. Eine GUI kann je nach Umsetzungsart (Desktop-Anwendung, Browser-Anwendung) unterschiedliche Anforderungen an die Architektur stellen. Die Software wird daher möglichst modular konzipiert, sodass diese später zu einer GUI weiterentwickelt werden kann.

Für eine automatisierte Prüfung der Bildinhalte auf Basis von traditioneller Bildverarbeitung oder moderner Verfahren der Künstlichen Intelligenz, ist Java leider nicht die ideale Grundlage. Hier wäre die Entwicklung einer Python-Anwendung sinnvoller. 

## Architekturvorschlag

Grundlegend
- Java Anwendung

Metadatenextraktion
- implementiert als Module
  - Modul 1: über [JHOVE](https://jhove.openpreservation.org/) (LGPL)
    - direkt eingebunden als Softwarebibliothek 
  - Modul 2: über [ExifTool](https://exiftool.org) (Perl License)
    - durch Starten eines Subprozesses (CLI)
    - eventuell mit Hilfe von [`com.github.mjeanroy/exiftool-lib`](https://github.com/mjeanroy/exiftool) (Apache 2.0)
    - oder anhand der XML-Ausgabe (`exiftool -X`)

Konfigurationsdatei lesen
- im YAML oder JSON Format
- mit [`jackson-databind`](https://github.com/FasterXML/jackson-databind) (Apache 2.0)

CSV Datei schreiben
- mit [`opencsv`](https://opencsv.sourceforge.net/) (Apache 2.0)

Prüflogik
- eigene Implementierung
- eventuell Parsen der Regeln mit [ANTLR](https://github.com/antlr/antlr4) (BSD)

## Kommdozeilenschnittstelle

### Parameter

`spk-iv-cli [-v] [--config FILE] [--csv FILE] [-r RULE ...] DIRECTORY`

- `-v, --verbose` - print additional log messages to stderr
- `--config` - path to configuration file
- `--csv` - path to generated CSV file
- `-r, --rule` - additional validation rules

Zusätzliche Regeln

`"KEY OPERATOR VALUES"`, e.g. `"IFD0:Compression = Uncompressed"`
- `KEY` - path to metadata key, e.g. `IFD0:Compression`
- `OPERATOR` - comparison operator, e.g. `=`
- `VALUES` - comma-separated comparison values, e.g. `Uncompressed`

Beispiel

```
java -jar spk-iv-cli.jar \ 
  --verbose \
  --config /path/to/config.yaml \
  --csv /path/to/output.csv \
  -r "IFD0:Compression = Uncompressed" \
  /path/to/directory
```

### Kommandozeilenausgabe

#### Stdout 

Ausgabe eines JSON Dokument pro Zeile, sodass der Prüfstatus für alle Bilddateien und Ordner live mitverfolgt aber auch weiterverarbeitet werden kann:
  - `time` - aktuelle Uhrzeit
  - `type` - Prüfnachricht für `file` oder `directory`
  - `path` - Dateipfad zur Bilddatei oder dem Ordner
  - `validation` - `success` falls erfolgreich, sonst `failed`
  - `error` - Fehlernachricht

Beispiel
```
{"time": "2026-01-28 10:21:00.123", "type": "file", "path": "/path/to/image_000001.tif", "validation": "success", "error": null}
{"time": "2026-01-28 10:21:00.456", "type": "file", "path": "/path/to/image_000002.tif", "validation": "failed", "error": "rule 'Compression = uncomressed' did not match"}
{"time": "2026-01-28 10:21:00.678", "type": "directory", "path": "/path/to", "validation": "failed", "error": "1 image with validation errors"}
```

Stderr

```
[2026-01-28 10:21:00.123 INFO] processing image '/path/to/image_000001.tif'
[2026-01-28 10:21:00.234 INFO] validation successful for image '/path/to/image_000001.tif'
[2026-01-28 10:21:00.345 INFO] processing image '/path/to/image_000002.tif'
[2026-01-28 10:21:00.456 ERROR] validation error for image '/path/to/image_000002.tif', rule 'Compression = uncomressed' did not match
[2026-01-28 10:21:00.567 INFO] finished processing directory '/path/to'
[2026-01-28 10:21:00.678 ERROR] directory '/path/to' had 1 image with validation errors 
```

### Exit Codes

- `0` - no program errors, validation finished without errors
- `1` - generic program error, validation aborted
- `2` - no program errors, validation finished with errors


### Weiterverarbeitung der Kommandozeilenausgabe

Die zeilenbasierte Ausgabe von JSON-Dokumenten kann mit `jq` (Linux, Bash) und `ConvertFrom-Json` (Windows, Powershell) geparsed und zum Auslösen weiterer Aktionen (z.B. Verschieben der Dateien) genutzt werden, z.B:

Für Linux:

```
java -jar spk-iv-cli.jar --config /path/to/config.yaml /path/to/directory \
\
| while read -r LINE; do
  VALIDATION=$(jq -r '.validation' <<< "$LINE")
  FILEPATH=$(jq -r '.path' <<< "$LINE")

  case "$VALIDATION" in
    success)
      echo "Sucess for $FILEPATH"
      ;;
    failed)
      echo "Error for $FILEPATH"
      ;;
  esac
done
```
